# 4. 비용 — 자체 GPU의 작은 모델(SLM) 대 매니지드 API

**한국어** | [English](04_cost_en.md)

공통 조건은 [0. 실험 설정](00_setup.md)에 있습니다. 이 문서의 비용은 모두 **계산값**이고, 청구서에서 가져온 값이 아닙니다.
- **자체 GPU(①·②):** [2](02_int4_quantization.md)·[3](03_vllm_serving.md)에서 잰 시간과 처리량에 GPU 시간당 정가를 곱했습니다.
- **매니지드 API(③):** API가 돌려준 사용 토큰 수에 토큰당 정가를 곱했습니다.

## 어떻게 계산했나

```text
1,000문항당 비용 = (시간당 가격 ÷ 3,600) × 걸린 초 ÷ 문항 수 × 1,000
```

토크나이저가 모델마다 달라 토큰당 비용은 비교하기 어렵습니다. 그래서 문항 수로 나눴습니다.

| 가격 | 값 | 출처 |
|---|---|---|
| 온디맨드 | 시간당 $6.98 | Azure Retail Prices API, `Standard_NC40ads_H100_v5`, West US 2, Linux |
| Spot | 시간당 $3.537 | 같은 API, 2026-11-01 기준. Spot 가격은 수시로 바뀌고, 쓰는 중에 회수될 수 있습니다 |

두 값 모두 공개 정가입니다. 계약 할인은 넣지 않았습니다. Spot 가격만 쓰면 자체 GPU가 실제보다 싸 보이므로 두 값을 같이 적습니다.

## ① 시험 3,009문항을 한꺼번에 넣어 풀 때 (측정한 시간으로 계산)

`eval_vllm.py`가 3,009문항을 vLLM에 한꺼번에 넣고 답이 다 나올 때까지 걸린 시간입니다. 모델 불러오는 시간은 뺐습니다.

![시험 3,009문항을 한 번에 넣어 풀 때 1,000문항당 GPU 비용](figures/cost_per_1k.svg)

| 모델 | 3,009문항에 걸린 시간 | 1,000문항당, 온디맨드 | 1,000문항당, Spot |
|---|---|---|---|
| BF16 LoRA | 17.27초 | **$0.0111** | $0.0056 |
| INT4 PTQ | 266.21초 | $0.1715 | $0.0869 |
| INT4 QAT | 266.27초 | $0.1716 | $0.0869 |

한꺼번에 많이 처리하는 일에서는 BF16이 INT4보다 15배 쌉니다. [3. vLLM 서빙](03_vllm_serving.md)에서 본 대로, 이번 INT4 형식은 큰 배치에서 느리기 때문입니다.

## ② 서버로 받을 때 (측정한 처리량으로 계산)

[3. vLLM 서빙](03_vllm_serving.md)의 온라인 서빙에서 잰 초당 처리 요청을 넣었습니다. 서버가 쉬지 않고 계속 요청을 받는다고 가정한 값이라 실제보다 낮게 나옵니다.

| 조건 | BF16: 초당 요청 → 1,000문항당 온디맨드 | INT4: 초당 요청 → 1,000문항당 온디맨드 |
|---|---|---|
| 동시 1, prefix caching 끔 | 14.1 → $0.137 | 1.8 → $1.086 |
| 동시 1, prefix caching 켬 | 21.2 → $0.091 | 7.6 → $0.255 |
| 동시 64, prefix caching 끔 | 25.9 → $0.075 | 1.9 → $1.023 |
| 동시 64, prefix caching 켬 | 32.8 → **$0.059** | 11.1 → $0.175 |

"켬"은 동시 요청 수마다 새 문항을 보내, 모든 요청에 같은 앞부분(530토큰)만 캐시에서 다시 쓴 값입니다(2026-11-14 측정).

Spot이면 각 값의 약 절반입니다(× 3.537 / 6.98).

**본 것.**
- 비용은 모델보다 **어떻게 서빙하느냐**에 더 크게 좌우됩니다.
- 같은 INT4 모델이라도 동시 64에서 prefix caching을 끄면 1,000문항에 $1.023, 켜면 $0.175입니다. 약 6배 차이입니다.
- 서빙 방식이 같으면 BF16이 INT4보다 쌉니다. 동시 64·켬에서 $0.059 대 $0.175입니다.
- 이번 H100 측정에서 BF16 LoRA는 어느 조건에서도 1,000문항당 온디맨드 $0.14를 넘지 않았습니다.

## ③ 매니지드 API와 비교 — SLM 대 API

같은 2022~2024년 3,009문항을 Azure AI Foundry의 매니지드 API 모델 11개에도 풀게 했습니다. 문항, 시스템 문구, 질문 문구, 채점은 Mi:dm과 같습니다. 다른 점은 두 가지입니다.
- **프롬프트:** Mi:dm 채팅 템플릿이 스스로 붙이는 KT 시스템 블록(약 450토큰)과 날짜 줄이 API 요청에는 없습니다.
- **생성 설정:** Mi:dm은 greedy로 최대 16토큰을 만듭니다. API 모델은 모델 기본 설정으로 최대 2,048토큰까지 만듭니다.

> **측정 조건**
> - 실행: 2026-11-12, Azure AI Foundry, 배포 유형 Global Standard, 미국 동부 2 리소스, 모델마다 1회
> - 요청: Chat Completions, `max_completion_tokens` 2,048. `temperature`와 `reasoning_effort`는 보내지 않아 모델 기본값을 썼습니다. 동시 요청은 모델별 요청 한도에 맞춰 12~32개였습니다
> - 인증: Microsoft Entra ID(`az` 로그인). API 키는 쓰지 않았고, 결과 파일에 엔드포인트 주소를 남기지 않았습니다
> - 가격: Azure Retail Prices API(Foundry Models, eastus2, Global Standard)에서 2026-11-12에 읽은 공개 정가입니다. 문맥 길이로 가격이 갈리는 모델은 짧은 문맥 가격을 썼습니다. 계약 할인은 넣지 않았습니다
> - 순서: 먼저 2021년 문제 30문항으로 토큰 수와 오류를 확인했습니다(파일럿, 레포에 넣지 않음). 그다음 2022~2024년 문제를 모델마다 한 번 쟀습니다

"서버, 동시 1"은 ②의 prefix caching 끔 값이고, 2021년 문제 256개로 잰 처리량에서 계산했습니다. 숫자는 모두 [`compare_final_managed.json`](../../quantization/results/kormedmcqa_midm/managed/compare_final_managed.json)에서 나옵니다(서버 값은 그 파일의 `server_c1_cacheoff`).

**본 것.**
- 매니지드 모델 11개 중 10개가 튜닝한 Mi:dm BF16 LoRA(72.3%)보다 정답률이 높았습니다. 가장 높은 세 모델(gpt-6-astra, gpt-6.1-sol, gpt-5.6-sol)은 97.5~98.4%입니다.
- gpt-5.4 계열의 가장 아래 등급인 gpt-5.4-nano(64.9%)만 Mi:dm보다 낮았습니다. 같은 문항 비교에서도 Mi:dm만 맞힌 문항이 514개, nano만 맞힌 문항이 291개입니다.
- 3,009문항을 한꺼번에 풀면 자체 H100의 BF16 LoRA가 1,000문항당 $0.0111로 가장 쌉니다. 그다음은 gpt-5.4-nano $0.0459, llama-4-maverick $0.0509입니다.
- 서버로 한 요청씩 받으면(동시 1, prefix caching 끔) 자체 H100의 BF16 LoRA는 $0.137입니다. 이 조건에서는 gpt-6-luna(95.9%, $0.0836)가 정답률과 비용 둘 다 앞섭니다. deepseek-v4-1-flash, llama-4-maverick도 둘 다 앞섭니다.
- 매니지드 모델마다 7~10문항이 Azure 콘텐츠 필터에 막혔습니다. HTTP 400 오류가 와 답을 받지 못했고, 오답으로 셌습니다. 막힌 문항은 모두 11개이고, 그중 7개는 11개 모델 전부에서 막혔습니다. 모델별 막힘을 모두 더하면 의사 67건, 간호사 19건, 치과의사 1건입니다. 자체 GPU에서는 막힌 문항이 없습니다.
- 출력 길이가 2,048토큰 한도에 걸려 답이 없던 문항이 gpt-6-luna 13개, gpt-oss-120b 13개, gpt-5.6-sol 2개입니다. 이 문항도 오답으로 셌습니다.
- 보기 번호가 아닌 숫자로 답해 오답이 된 문항이 mistral-medium-3-5 6개, deepseek-v4-1-flash 3개, gpt-5.4-mini 3개, gpt-5.4-nano 2개입니다(예: "350", "1.8"). 자체 GPU 모델에서는 0개였습니다.
- 프롬프트는 Mi:dm이 654토큰, API 요청이 193~268토큰입니다. 토크나이저가 달라 바로 비교할 수는 없지만, 차이의 대부분은 Mi:dm 템플릿의 고정 시스템 블록(Mi:dm 토크나이저로 약 450토큰)입니다.

**그럴 법한 이유.**
- 정답률 차이는 모델 크기와 학습량 차이로 보는 것이 자연스럽습니다. 가장 높은 네 모델(95.9~98.4%)은 답하기 전에 문항당 15~116개의 추론 토큰을 썼습니다. 반면 gpt-5.4는 추론 토큰 없이 92.0%였습니다. Mi:dm LoRA는 답 번호만 배웠고 바로 답합니다. 이 실험은 이 설명들을 갈라 재지 않았습니다.
- 자체 GPU가 가장 싸게 나온 것은 GPU를 쉬지 않고 쓴다고 가정한 계산이기 때문입니다. 한 요청씩 받는 서버에서는 같은 GPU 비용이 훨씬 적은 문항에 나뉩니다.

**이 결과로 말할 수 없는 것.**
- **같은 크기끼리의 비교가 아닙니다.** 매니지드 모델은 크기가 공개되지 않았거나 Mi:dm(11.5B)보다 훨씬 큽니다. "작은 모델은 쓸모없다"나 "튜닝은 효과가 없다"로 옮기면 틀린 말이 됩니다.
- **매니지드 모델이 이 기출문제를 학습 때 봤는지 확인할 수 없습니다.** KorMedMCQA는 공개 자료입니다. 튜닝 전 Mi:dm에도 같은 한계가 있습니다.
- **비용 기준이 다릅니다.** 자체 GPU는 GPU 시간 × 정가이고, 쉬는 시간·운영 인력·디스크는 넣지 않았습니다. 매니지드 API는 쓴 토큰 × 정가입니다. 둘 다 공개 정가이고 계약 할인은 넣지 않았습니다.
- **모델마다 한 번씩 쟀습니다.** 매니지드 배포는 같은 이름이라도 모델 버전이 자동으로 바뀔 수 있습니다. GPT 계열 7개는 이번 실행의 버전이 결과 파일의 `models_reported`에 있고, 나머지 4개는 모델 이름만 돌려줘 버전을 남기지 못했습니다. 콘텐츠 필터 결과도 매번 같지는 않았습니다. 막힌 문항만 다시 보냈을 때 결과가 달라진 문항이 있었습니다(다시 보낸 기록은 레포에 넣지 않았습니다).
- **모델 설정은 기본값 그대로입니다.** `reasoning_effort` 같은 설정을 바꾸면 정답률과 비용이 달라질 수 있습니다.
- **지연 시간은 비교하지 않습니다.** 모델마다 요청 한도와 동시 요청 수가 달랐습니다.
- **정답률과 비용만 봤습니다.** 데이터가 회사 밖으로 나가는지, 모델 버전을 고정할 수 있는지, 콘텐츠 필터를 조정할 수 있는지는 이 표에 없습니다. 이런 조건은 쓰는 곳마다 따로 따져야 합니다.

**다시 돌리기.** GPU는 필요 없고, `az login`으로 Foundry 리소스에 접근할 수 있어야 합니다.

```bash
export MANAGED_BASE_URL=https://<리소스 이름>.services.ai.azure.com/openai/v1
export MANAGED_AZ_SUBSCRIPTION=<구독 이름 또는 ID>      # 토큰을 받을 테넌트를 고릅니다
# 파일럿: 2021년 문제 30문항 (2022~2024년 결과 파일은 건드리지 않습니다)
python -m quantization.eval_managed --config quantization/configs/kormedmcqa_midm.yaml \
    --deployment gpt-5.4-nano --split selection_dev --eval-size 30
# 본 측정: 2022~2024년 3,009문항, 모델마다 한 번 (가격은 USD/100만 토큰, 출처와 날짜를 같이 적습니다)
python -m quantization.eval_managed --config quantization/configs/kormedmcqa_midm.yaml \
    --deployment gpt-5.4-nano --concurrency 32 --region eastus2 \
    --price-in 0.2 --price-out 1.25 --price-cached-in 0.02 --price-source "Azure Retail Prices API ..., read <날짜>"
python -m quantization.managed_compare            # 짝지은 비교와 요약표
```

데이터 로더(`datasets` 4.3.0)는 Python 3.14에서 깨져 Python 3.12로 돌렸습니다.

## 이 결과로 말할 수 없는 것 (자체 GPU 쪽)

- **GPU 사용 시간만 셌습니다.** 서버가 노는 시간, 모델 불러오는 시간, 디스크, 네트워크, 운영하는 사람의 시간은 넣지 않았습니다. 실제 비용은 이보다 큽니다.
- **②는 가정이 들어간 계산입니다.** 서버가 쉬지 않고 바쁘다고 가정했습니다. prefix caching을 켠 값은 모든 요청에 같은 앞부분(530토큰)만 캐시에서 다시 쓴 경우입니다. 같은 질문이 반복되면 더 싸질 수 있지만 재지 않았습니다([3. vLLM 서빙](03_vllm_serving.md#시험-답-요청-답-12토큰)).
- **H100 NVL 한 종류, 공개 정가 기준입니다.** 다른 GPU, 다른 지역, 계약 가격에서는 달라집니다.
- **INT4가 비싸게 나온 것은 이번 INT4 형식(TorchAO tile-packed)의 결과입니다.** INT4 일반의 결론으로 옮기면 틀린 말이 됩니다.
